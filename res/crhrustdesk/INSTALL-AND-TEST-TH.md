# คู่มือติดตั้งและทดสอบ CrhRustDesk

ใช้กับตัวติดตั้ง Ubuntu ชุดวันที่ 14 พฤศจิกายน 2569 บน Windows 10 หรือ 11 x64 เซิร์ฟเวอร์ติดตั้งแล้ว คู่มือนี้เป็นขั้นตอนทดสอบเครื่องจริง ซึ่งยังต้องบันทึกผลหลังดำเนินการ

| รายการ | ค่าที่ใช้ทดสอบ |
| --- | --- |
| Server Ubuntu | `172.16.1.83` |
| Account API | `https://172.16.1.83:8443` |
| Active Directory | `crhdomain.local` ที่ `172.16.1.10` |
| เครื่องปลายทางที่รับ remote | `172.29.0.52` |
| เครื่อง IT ที่ควบคุม | `172.29.0.96` |
| ตัวติดตั้ง | `CrhRustDesk-Setup.exe` ในโฟลเดอร์ `target/CrhRustDesk-Ubuntu-Setup` |

ลำดับทำงาน: ติดตั้งเครื่องปลายทางตามส่วนที่ 1 ติดตั้งและ Login เครื่อง IT ตามส่วนที่ 2 จากนั้นกำหนดสิทธิ์ในส่วนที่ 3 แล้วกลับมาทดสอบการเชื่อมต่อในส่วนที่ 2

หากใช้ IP เครื่องอื่น ต้องเพิ่ม IP ใน Firewall ของ Ubuntu และปรับ rule ที่เครื่องปลายทางก่อน ชุดปัจจุบันอนุญาตเฉพาะสองเครื่องในตาราง

## 1. ติดตั้งและตรวจเครื่อง client ปลายทาง

เครื่องนี้เป็นคอมพิวเตอร์ของผู้ใช้ที่อนุญาตให้ IT รีโมตเข้า ตัวอย่างคือ `172.29.0.52`

### 1.1 ตรวจไฟล์และติดตั้ง

1. คัดลอก `CrhRustDesk-Setup.exe` จากชุด Ubuntu ไปยังเครื่องปลายทาง
2. ปิด CrhRustDesk รุ่นเก่าจากเมนู tray ข้างนาฬิกา หากมีแอป remote ตัวอื่นที่องค์กรใช้อยู่ ให้คงไว้ระหว่างทดสอบ
3. ตรวจ SHA-256 ของตัวติดตั้งใน PowerShell จากโฟลเดอร์ที่เก็บไฟล์:

```powershell
Get-FileHash .\CrhRustDesk-Setup.exe -Algorithm SHA256
```

ผลที่ตรงกับชุดนี้คือ:

```text
77102DBA952370400AFE0AC76CFBA19B1F0E715BC0F563D09D90DACA15162669
```

4. ดับเบิลคลิก Setup แล้วให้บัญชี Windows ที่มีสิทธิ์ Administrator อนุญาตการติดตั้ง
5. เลือก **เครื่องปลายทาง — รับการรีโมตเข้าเท่านั้น**
6. ตรวจ Server เป็น `172.16.1.83` และ Account API เป็น `https://172.16.1.83:8443`
7. ตรวจค่า SHA-256 ของไฟล์ CA ที่หน้าติดตั้งให้ตรงกับค่านี้ แล้วเลือกยอมรับ CA ภายในเมื่อผู้ดูแลอนุมัติให้เชื่อถือทั้งเครื่อง:

```text
38441E1FCC1EE29CFADD0F25F97F9A33875CDECAB4569BE8C26288A00F1AF351
```

8. กด Install แล้ว Finish จากนั้นเปิด CrhRustDesk จาก Start Menu หรือ Desktop

ตัวติดตั้งยังไม่มีลายเซ็นดิจิทัล หากนโยบายองค์กรบล็อก ให้ผู้ดูแลตรวจไฟล์ตามนโยบายก่อนติดตั้ง ไม่ต้อง import certificate ด้วยคำสั่งเองเมื่อ Setup ทำสำเร็จ

### 1.2 ตรวจหลังติดตั้ง

1. รอให้แอปแสดง Ready หรือสถานะพร้อมเชื่อมต่อ ต้องไม่ค้างที่ Connecting
2. จด ID ที่แอปแสดง โดยใช้เลขต่อกัน เช่น `123456789` สำหรับนำไปกำหนดสิทธิ์ ตัวเลขนี้เป็นตัวอย่าง ให้ใช้ ID จริงของเครื่อง
3. ตรวจว่า IP ที่หน้าแอปและเมนู tray มี `172.29.0.52` หากมีหลาย adapter ให้เลือก IP ที่เครื่อง IT ติดต่อถึง
4. ตรวจว่าหน้าเครื่องปลายทางไม่มีส่วนให้เริ่มรีโมตออก
5. ตรวจ Windows service ด้วย PowerShell:

```powershell
Get-Service -Name '*CrhRustDesk*' | Select-Object Name, Status, StartType
```

ผลที่ต้องการคือพบบริการรับ remote ของ CrhRustDesk และสถานะ Running เครื่องปลายทางไม่ต้อง Login ด้วยบัญชี IT และไม่ต้องบันทึกรหัส AD ลงเครื่อง

ถ้าต้องตรวจบทบาทและค่า server ให้อ่านไฟล์นี้:

```powershell
Get-Content 'C:\Program Files\CrhRustDesk\connection-profile.json'
```

ค่าที่คาดหวังคือ `role` เป็น `incoming`, `id_server` เป็น `172.16.1.83` และ `api_server` เป็น `https://172.16.1.83:8443` หากผิด ให้รัน Setup ที่ถูกชุดอีกครั้ง

**ผ่านส่วนที่ 1 เมื่อ:** แอปพร้อมเชื่อมต่อ มี ID และ IP ถูกต้อง บริการทำงาน และเลือกบทบาท incoming แล้ว

## 2. ติดตั้งและทดสอบเครื่อง IT ที่ใช้ควบคุม

ตัวอย่างเครื่องควบคุมคือ `172.29.0.96` ใช้บัญชี AD ของเจ้าหน้าที่แต่ละคนสำหรับ Login ในแอป

### 2.1 ติดตั้งและ Login

1. ใช้ Setup ไฟล์เดียวกับส่วนที่ 1 และตรวจ SHA-256 ก่อนติดตั้ง
2. ให้สิทธิ์ Windows Administrator เมื่อติดตั้ง แล้วเลือก **เครื่อง IT — รีโมตออกไปยังเครื่องอื่นเท่านั้น**
3. ตรวจ Server, Account API และ CA เช่นเดียวกับส่วนที่ 1 แล้วติดตั้งให้เสร็จ
4. เปิด CrhRustDesk จาก Start Menu แล้วเปิดเมนูบัญชีเพื่อ Login
5. กรอก username ของ AD แบบ `sAMAccountName` เช่น `AD_USERNAME` และรหัสผ่าน AD ของบัญชีนั้น ไม่ต้องเติม `crhdomain.local` ในช่อง username
6. ตรวจว่าชื่อบัญชีที่ Login ตรงกับบัญชีที่จะให้สิทธิ์ใน Management

ใช้บัญชีที่มีอยู่จริงใน AD และเปิดใช้งานอยู่ หากยังไม่มี `AD_USERNAME` ใน AD ให้เลือก username จริงของเจ้าหน้าที่ก่อนให้สิทธิ์

หากอ่าน `connection-profile.json` บนเครื่องนี้ ค่า `role` ต้องเป็น `outgoing` เครื่อง IT บทบาทนี้ไม่รับการรีโมตเข้า จึงไม่ต้องใช้สถานะ service รับ remote เป็นเกณฑ์ตรวจเครื่อง IT

### 2.2 ตรวจการเข้าถึงเครือข่าย

รันจากเครื่อง IT:

```powershell
Test-NetConnection 172.16.1.83 -Port 8443
Test-NetConnection 172.16.1.83 -Port 21115
Test-NetConnection 172.16.1.83 -Port 21116
Test-NetConnection 172.16.1.83 -Port 21117
Test-NetConnection 172.29.0.52 -Port 21118
```

ผลที่ต้องการคือ `TcpTestSucceeded : True` ทุกคำสั่ง พอร์ต `21118` คำสั่งสุดท้ายเป็นพอร์ตที่เครื่องปลายทาง Windows ไม่ใช่พอร์ตบน Ubuntu การตรวจนี้เป็น TCP และไม่ได้ยืนยันการรับส่ง UDP

หลังติดตั้ง CA แล้ว ตรวจ Account API เพิ่มได้ด้วย:

```powershell
(Invoke-WebRequest -UseBasicParsing -Uri 'https://172.16.1.83:8443/api/login-options').StatusCode
```

ผลที่ต้องการคือ `200` โดยไม่มี certificate error หากตรวจ certificate ไม่ผ่าน ให้ตรวจวันเวลาเครื่องและ CA ที่ติดตั้งก่อน

### 2.3 ทดสอบการรีโมตจริงหลังให้สิทธิ์ในส่วนที่ 3

| การทดสอบ | วิธีทำ | ผลที่ต้องการ |
| --- | --- | --- |
| เข้าโดย ID | ใส่ ID จริงของเครื่องปลายทาง แล้วกด Connect | เชื่อมต่อได้และแสดง desktop ของเครื่องที่ถูกต้อง |
| เข้าโดย IP | ปิด session แรก แล้วใส่ `172.29.0.52` เพื่อ Connect ใหม่ | เชื่อมต่อได้เช่นเดียวกับ ID |
| ไม่ต้องกดยอมรับ | ใช้บัญชี AD ที่ได้รับสิทธิ์ใน Management | เข้า desktop ได้โดยปลายทางไม่ต้องกดอนุมัติ หากเปิด 2FA ยังต้องผ่าน 2FA |
| แจ้งเตือนปลายทาง | ให้ผู้ใช้ปลายทางดูหน้าจอเมื่อเริ่ม session | มีหน้าต่างแสดงการเชื่อมต่อและชื่อบัญชี IT |
| แสดงภาพ | เปิดหน้าต่างงานบนปลายทาง | เครื่อง IT เห็นภาพตรงกับเครื่องปลายทาง |
| เมาส์และคีย์บอร์ด | เปิด Notepad แล้วพิมพ์ข้อความทดสอบ เลื่อนและคลิกเมาส์ | ผู้ใช้ปลายทางเห็นข้อความและการเคลื่อนไหวตามจริง |
| หยุดจากปลายทาง | ให้ผู้ใช้ปลายทางหยุด session จากหน้าต่างการเชื่อมต่อ | เครื่อง IT หลุดจาก session |
| ทำงานหลัง reboot | นัดผู้ใช้แล้ว restart เฉพาะเครื่องปลายทาง จากนั้นรอ service พร้อม | IT เชื่อมต่อใหม่ได้ โดยไม่ต้องเปิด portable รุ่นเก่า |

ทดสอบ desktop ก่อน การรับส่งไฟล์แยก session, terminal, camera และ tunnel ไม่รวมอยู่ในสิทธิ์ desktop ชุดนี้ ไม่ใช้ผลการทดสอบเหล่านั้นตัดสินว่าสิทธิ์ desktop ผ่านหรือไม่

**ผ่านส่วนที่ 2 เมื่อ:** บัญชี AD Login ได้ เข้าทั้ง ID และ IP ได้ ภาพกับการควบคุมทำงาน ปลายทางเห็นการแจ้งเตือนและหยุด session ได้

## 3. ให้สิทธิ์เจ้าหน้าที่ IT และทดสอบการจำกัดสิทธิ์

### 3.1 แยกประเภทบัญชี

| บัญชีหรือสิทธิ์ | ใช้ทำอะไร |
| --- | --- |
| Windows Administrator | อนุญาตให้ติดตั้งแอปและบริการบน Windows |
| บัญชี AD ของเจ้าหน้าที่ เช่น `AD_USERNAME` | Login แอปบนเครื่อง IT และรีโมตตามสิทธิ์รายเครื่อง |
| CrhRustDesk `admin` | เข้า Management เพื่อกำหนดสิทธิ์ผู้ใช้ นโยบายปัจจุบันอนุญาตรีโมตทุกเครื่องด้วย |
| Ubuntu `SSH_USER` | SSH เข้าดูแล Ubuntu และเปิด tunnel สำหรับหน้า Management |
| AD `LDAP_READER` | บัญชี service สำหรับอ่าน AD ไม่ใช้เป็นบัญชีเจ้าหน้าที่รีโมต |

หน้า Management ปัจจุบันกำหนดสิทธิ์ remote ให้ username ของ AD ได้ การกดอนุญาตไม่ได้เพิ่มสิทธิ์ผู้ดูแล Management และไม่ได้เปลี่ยนสิทธิ์ Windows ของบัญชีนั้น ปัจจุบันใช้ local `admin` สำหรับบริหาร Management ยังไม่มีตัวเลือกในหน้านี้ให้แต่งตั้งบัญชี AD เป็นผู้ดูแล Management

### 3.2 เข้า Management ผ่าน LAN

1. จากเครื่องใน LAN `172.16.0.0/16` หรือ `172.29.0.0/24` เปิด **https://172.16.1.83:21120/_admin/** โดยใช้ HTTPS หน้านี้เป็น Admin เต็มสำหรับดูแลผู้ใช้ ดู log และเปลี่ยนรหัส local admin
2. ใช้เครื่องที่เชื่อถือ CA ภายในของ Ubuntu แล้ว เช่น เครื่องที่ติดตั้ง CrhRustDesk ชุดนี้ หากมี certificate error ให้ตรวจ CA และวันเวลาเครื่องก่อน
3. Login ด้วย username `admin` และรหัส CrhRustDesk ของบัญชีนี้ รหัสเริ่มต้นอ่านได้ด้วยคำสั่ง SSH ด้านล่าง หากเปลี่ยนรหัสไปแล้ว ให้ใช้รหัสล่าสุด
4. สำหรับกำหนดสิทธิ์ remote ให้เปิด **https://172.16.1.83:21120/_permissions/** แล้ว Login ด้วย `admin` อีกครั้ง จากนั้นทำตามส่วนที่ 3.3 ไม่ต้องเปิด SSH tunnel สำหรับสอง URL นี้

เปลี่ยนรหัส local `admin` จากหน้า Admin เต็ม โดยเปิด **User Info** แล้วกด **Change Password** ที่หัวข้อ Password กรอกรหัสเดิมและรหัสใหม่ให้ครบ เมื่อบันทึกสำเร็จให้ออกจากระบบแล้ว Login ใหม่ด้วยรหัสใหม่ รหัส AD เปลี่ยนที่ระบบ AD

`127.0.0.1` ใช้กับเครื่องที่กำลังเปิด browser เท่านั้น การเข้าจาก LAN ให้ใช้ IP Ubuntu `172.16.1.83` ตาม URL ด้านบน

### ทางเลือก: เข้า Management ผ่าน SSH tunnel

1. ใช้เครื่องจัดการที่พอร์ต local `21120` ว่าง ตรวจได้ด้วย:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 21120 -ErrorAction SilentlyContinue
```

หากไม่มีผลลัพธ์ พอร์ตนี้ว่าง หากพบ process ให้ตรวจเจ้าของพอร์ตก่อน เครื่อง dev เดิมมี Management ของ dev ใช้พอร์ตนี้อยู่ ให้ใช้เครื่อง IT อีกเครื่องที่พอร์ตว่าง เพื่อไม่เข้าไปกำหนดสิทธิ์ผิด server

2. เปิด PowerShell แล้วรัน tunnel โดยใช้รหัส Ubuntu ของ `SSH_USER` เมื่อ SSH ขอ คงหน้าต่างนี้ไว้:

```powershell
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:21120:127.0.0.1:21120 SSH_USER@172.16.1.83
```

3. เปิด PowerShell อีกหน้าต่าง แล้วอ่านรหัสเริ่มต้นของ CrhRustDesk `admin` ผ่าน SSH ส่วนตัว:

```powershell
ssh -t SSH_USER@172.16.1.83 "sudo cat /etc/crhrustdesk/admin-initial-password"
```

หากเปลี่ยนรหัส admin ไปแล้ว ให้ใช้รหัสล่าสุด ไฟล์นี้เก็บรหัสเริ่มต้นเท่านั้น ไม่ต้องส่งรหัสในแชตหรือแนบไว้กับคู่มือ

4. เปิด `http://127.0.0.1:21120/_admin/` ใน browser แล้ว Login ด้วย username `admin` และรหัส CrhRustDesk ของบัญชีนี้

อย่าเปิดหน้า Management ด้วย `https://172.16.1.83:8443/_admin/` เส้นทางนี้ถูกปิดจาก LAN และจะตอบ 403 ตามการตั้งค่า

### 3.3 ให้สิทธิ์รีโมต

1. ในหัวข้อ **สิทธิ์รีโมตตาม username** ระบุบัญชี AD ในช่อง **Username ที่ต้องการกำหนดสิทธิ์** เช่น `AD_USERNAME`
2. เลือก **อนุญาตให้รีโมตโดยแจ้งเตือนปลายทาง ไม่ต้องกดยอมรับ**
3. สำหรับทดสอบรายเครื่อง ให้ไม่เลือก **อนุญาตทุกเครื่องปลายทาง** แล้วกรอก ID จริงของเครื่อง `172.29.0.52` ในช่อง ID ห้ามกรอก IP ลงช่องนี้
4. ถ้าต้องการหลายเครื่อง ให้กรอก ID คั่นด้วย comma เช่น `123456789,987654321` โดยแทนด้วย ID จริง
5. หากหน้าที่งานต้องเข้าทุกเครื่อง ให้เลือก **อนุญาตทุกเครื่องปลายทาง** แทนการกรอก ID
6. กด **บันทึกสิทธิ์** แล้วตรวจข้อความว่าบันทึก username นั้นสำเร็จ
7. ให้เจ้าหน้าที่ Login บัญชีเดียวกันบน client แล้วทดสอบตามส่วนที่ 2.3

หากบัญชี AD ยังไม่ปรากฏในรายการ สามารถพิมพ์ username โดยตรงได้ หรือให้ Login ใน client ครั้งแรกแล้วค้นหาใหม่ ใช้ชื่อให้ตรงกับชื่อที่ระบบแสดงหลัง Login

ก่อนทดสอบให้ตรวจสิทธิ์เดิมของบัญชี AD ใน Management เมื่อต้องทดสอบจำกัดรายเครื่อง ให้บันทึกเฉพาะ ID ทดสอบหรือใช้บัญชี AD ทดสอบอีกบัญชี ค่า `AD_USERNAME` เป็น placeholder อย่าใช้ `admin` ทดสอบข้อจำกัดรายเครื่อง เพราะนโยบาย admin ให้เข้าทุกเครื่อง

### 3.4 ทดสอบการให้และถอนสิทธิ์

| กรณี | วิธีทดสอบ | ผลที่ต้องการ |
| --- | --- | --- |
| ผู้ใช้ได้รับสิทธิ์ | ให้ ID ของเครื่อง A แล้วเชื่อมต่อ A | เชื่อมต่อได้โดยมีการแจ้งเตือน |
| ผู้ใช้ไม่มีสิทธิ์เครื่องอื่น | ให้เฉพาะ A แล้วลองเชื่อมต่อเครื่อง B ที่ลงทะเบียนกับ server และยังไม่มี grant | ถูกปฏิเสธ ไม่สามารถกดยอมรับที่ปลายทางเพื่อข้ามสิทธิ์ได้ |
| Login ได้แต่ยังไม่ให้สิทธิ์ | ใช้บัญชี AD ทดสอบที่ยังไม่มี grant แล้วลองเข้าเครื่อง A | Login สำเร็จ แต่เข้า desktop ไม่ได้ |
| ถอนสิทธิ์ | เอาเครื่องหมายอนุญาตออก แล้วกดบันทึก ปิด session เดิม รอเกิน 60 วินาที แล้วเชื่อมต่อใหม่ | เข้า desktop ไม่ได้ |
| เปิด Management ด้วยบัญชี IT ทั่วไป | ออกจาก Management แล้วลอง Login ด้วยบัญชี AD ของ IT ที่ได้รับเฉพาะสิทธิ์ remote | เข้า Management ไม่ได้ |

การถอนสิทธิ์หยุดการออก permit ใหม่ Permit ที่ออกไปแล้วมีอายุได้ถึง 60 วินาที และไม่ได้ตัด session ที่เปิดอยู่ ให้ปลายทางหยุด session นั้นก่อนทดสอบเชื่อมต่อใหม่

ถ้ามีบัญชี AD สำหรับทดสอบโดยเฉพาะ ให้ผู้ดูแล AD ทดสอบ disable บัญชีนั้น แล้วตรวจว่า Login หรือขอสิทธิ์เชื่อมต่อใหม่ไม่ได้ การ disable บัญชีไม่ได้หมายถึงตัด remote session ที่เปิดอยู่โดยทันที อย่าใช้บัญชี `LDAP_READER` สำหรับกรณีทดสอบนี้

**ผ่านส่วนที่ 3 เมื่อ:** ผู้ใช้เข้าได้เฉพาะเครื่องที่ให้สิทธิ์ บัญชีที่ไม่มีสิทธิ์เข้าไม่ได้ ถอนสิทธิ์แล้วเข้าใหม่ไม่ได้ และผู้ใช้ remote ทั่วไปเปิด Management ไม่ได้

## ตรวจเมื่อทดสอบไม่ผ่าน

| อาการ | ตรวจตามลำดับ |
| --- | --- |
| Connecting ค้าง หรือ ID does not exist | ตรวจว่าปลายทาง Ready, ทั้งสองเครื่องใช้ Setup Ubuntu ชุดเดียวกัน, profile ชี้ server ถูก และ TCP21115 ถึง 21117 กับ UDP21116 ผ่าน Firewall |
| `Failed to connect ...:21118` | ตรวจว่าปลายทางเปิดอยู่, service Running และทดสอบ TCP21118 จากเครื่อง IT ตรวจ rule `CrhRustDesk Service` ว่าอนุญาต IP เครื่อง IT และ Windows ใช้ Domain หรือ Private profile |
| Certificate error | ตรวจวันเวลาเครื่อง, API URL และ CA ของ Ubuntu ต้องตรงกับชุดนี้ |
| AD Login ไม่ผ่าน | ตรวจ username แบบ sAMAccountName, รหัสล่าสุด และสถานะบัญชี ให้ผู้ดูแลตรวจ LDAP กับ service account โดยไม่บันทึกรหัสลง log |
| Login ได้แต่ remote ถูกปฏิเสธ | ตรวจ username ใน Management, grant ของ ID จริง, ทั้งสองเครื่องใช้กุญแจชุด Ubuntu และ target 2FA ถ้ามี |
| SSH แจ้ง local port ใช้แล้ว | ปิดเฉพาะ tunnel เดิมที่ไม่ใช้งาน หรือใช้เครื่องจัดการอีกเครื่องที่พอร์ต21120 ว่าง ตรวจว่าไม่ได้เปิด Management ของ dev แทน Ubuntu |
| ให้สิทธิ์แล้วผู้ใช้ไม่ปรากฏในรายการ | ตรวจข้อความบันทึกสำเร็จ ให้บัญชีนั้น Login client ครั้งแรก แล้วค้นหาใหม่ |
